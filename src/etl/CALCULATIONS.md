# Расчёт кривых S2-04

Расчётный слой работает в памяти и отделён от источника, Excel и записи в БД.
Ручной и автоматический запуски должны вызывать одни и те же функции.
Парсер сохраняет `NA` в CSV; восстановление ставок выполняется загрузчиком
через `prepare_base_curve` непосредственно перед записью базовых точек.
Расчётный слой не создаёт заполненный CSV и не изменяет исходный файл.

## Единицы и дисконтирование

В `merged_zcyc_ranges.csv` ставки выражены в процентах. Адаптер `read_snapshots`
переводит их в доли ровно один раз: `13.28 -> Decimal('0.1328')`.
Внутри расчётов и в записях для БД используются доли; сроки — годы.

Экспортируемые значения КБД соответствуют спот-доходности с годовой
капитализацией. Внутренняя непрерывная ставка модели MOEX отличается от неё.
Поэтому для CSV MOEX и всех шести сценариев применяется:

```text
DF(r, t) = (1 + r)^(-t), r > -1
```

Основание: раздел 4 [методики MOEX](https://www.moex.com/ru/documents/14299),
редакция с 05.06.2024. Дополнительно выполнена численная сверка на 30.10.2026:
по параметрам модели на 18:54:59 непрерывные ставки на сроках 0.25 и 20 лет
составляют примерно 12.467108% и 15.515768%; после преобразования к годовой
капитализации — 13.277579% и 16.784209%, что соответствует CSV 13.28% и 16.78%.

Контрольные примеры: при `r=0.1, t=1` коэффициент равен
`0.90909090909090909090909090909090909091`; при `r=0.21, t=0.5` — тот же
коэффициент. При нулевой ставке DF равен 1. Отрицательная ставка допустима,
если она больше -100%; тогда коэффициент может превышать 1.
Это единственный способ дисконтирования в проекте; выбора соглашения нет.
Коэффициент рассчитывается одинаково для базовой кривой и всех сценариев.

## Восстановление пропусков при загрузке

`RawSnapshot` содержит дату, время и ставки в долях; отсутствующая ставка —
`None`. Перед загрузкой `prepare_base_curve` формирует все 12 базовых точек:

- Внутри диапазона наблюдений применяется линейная интерполяция между
  соседними известными сроками.
- На краях применяется линейная экстраполяция по двум крайним известным точкам.
- Формула: `r(t) = r(a) + (r(b) - r(a)) * (t - a) / (b - a)`.
- Опорные ставки берутся только из исходных наблюдений того же снимка.
  Рассчитанные точки и другие даты/моменты времени не используются как опорные.
- Ноль считается наблюдением. Известные ставки сохраняются без изменения.
  Нижняя граница на базовую кривую не накладывается.
- Если известно меньше двух ставок, возникает `DataValidationError` с датой
  и временем снимка. Заполнить такой снимок расчётный слой не пытается.

У полученных точек выставлены `is_interpolated`, `is_extrapolated`; у исходных
обе отметки `false`. `is_deleted` по умолчанию `false`.
Ставки и дисконтирование рассчитываются с `Decimal` при точности 38 значащих
цифр, без округления для отображения. Масштаб колонок PostgreSQL применяется
драйвером при записи: ставки `NUMERIC(18,10)`, DF `NUMERIC(28,18)`.

## Шесть сценариев

Формы шоков соответствуют формулам приложения 2
[BCBS d368](https://www.bis.org/publications/201604-standards-interest-rate-risk-banking-book.pdf).
Параметры вынесены в `ScenarioParameters`. По таблице, переданной куратором,
для RUB по умолчанию используются параллельный шок 400 б.п., короткий 500 б.п.
и длинный 300 б.п. (4, 5 и 3 процентных пункта). Затухание — 4 года, floor — 0.
Три амплитуды можно задавать независимо через Python API.

Для долей ставки `P = parallel_bps / 10000`,
`S = short_bps / 10000 * exp(-t / decay_years)`,
`L = long_bps / 10000 * (1 - exp(-t / decay_years))`:

| Сценарий | Добавка к базовой ставке |
| --- | --- |
| `Parallel_Up` | `+P` |
| `Parallel_Down` | `-P` |
| `Short_Up` | `+S` |
| `Short_Down` | `-S` |
| `Steepener` | `-0.65*S + 0.9*L` |
| `Flattener` | `+0.8*S - 0.6*L` |

Коэффициенты также доступны в `ScenarioParameters`. Ко всем шести сценариям
применяется единое правило `max(floor, base + shift)`, по умолчанию `floor=0`.
`floor=None` отключает ограничение. Затем DF рассчитывается заново по ставке
соответствующего сценария. HTML-иллюстрация использует те же формулы и floor.

Полный набор параметров сериализуется в JSON со строковыми десятичными числами.
Версия `irrbb_v1_<hash>` зависит от содержимого: изменение амплитуды, floor,
затухания или коэффициентов даёт другую версию. `definition_record()` возвращает
поля `scenario`, `version`, `parameters` для таблицы `stress_shocks`.

## Контракт загрузчика S2-05

Для одного снимка загрузчик выполняет следующую последовательность:

1. Создать `etl_runs` для ручного или автоматического запуска и сохранить его ID.
2. Получить `RawSnapshot` из merged CSV и вызвать `prepare_base_curve(snapshot)`.
3. Записать `CurvePoint(**point.record(etl_run_id))` для всех базовых точек.
4. Вызвать `calculate_scenarios(base_points, parameters)`.
5. Получить или создать версии `StressShock(**curve.definition_record())`.
6. Записать `StressCurve(**point.record(base_point_id, shock_id, etl_run_id))`.

Связь стрессовой точки с базовой определяется по сроку того же снимка.
На один снимок получается 12 базовых и 72 стрессовые точки. Интеграционные
тесты проверяют эти записи на действующей схеме PostgreSQL, в том числе
флаги восстановления и ссылки на запуск для обоих режимов.

Оркестрация реализована в `pipeline.run_pipeline`, CLI — `python -m src.etl.run`.
Все снимки одной даты публикуются одной транзакцией, а начало и итог запуска
записываются отдельно. Ошибка расчёта или записи не оставляет частичный набор
кривых. Правила повторной загрузки, исправления источника и версий сценариев
описаны в [PIPELINE.md](PIPELINE.md).

## Проверка расчёта и необязательный Excel

```powershell
python -m pip install -r requirements.txt
python -m src.etl.postprocessing --run-dir src/etl/downloads/ИМЯ_ЗАПУСКА
python -m src.etl.postprocessing --input path/to/merged_zcyc_ranges.csv --xlsx output/history.xlsx
python -m src.etl.postprocessing --run-dir src/etl/downloads/ИМЯ_ЗАПУСКА --shock-bps 500
```

Команда без `--xlsx` только читает CSV, считает в памяти и выводит статистику.
Без `--shock-bps` применяется набор RUB 400/500/300. Этот необязательный ключ
явно переопределяет все три амплитуды одинаковым значением для экспериментов.
Она не записывает данные в БД. Пути задаются явно; файл из случайного рабочего
каталога не выбирается. При экспорте создаются листы `Baseline`, шесть сценариев
и `Parameters`. Одна строка — одна точка кривой; ставки записаны в долях и
показаны процентным форматом Excel. Форматирование не изменяет расчётные
объекты; сами числовые ячейки Excel имеют обычную точность Excel.

Python API: `prepare_base_curve`, `calculate_scenarios`, `calculate_snapshot`,
`calculate_history`, `export_history_xlsx`. Совместимая обёртка
`generate_irrbb_history(input_file, output_file=None)` сохраняет Excel рядом
со входным файлом, если путь результата не указан. Восстановленные значения
существуют в памяти и в явно запрошенном Excel, исходный CSV с `NA` сохраняется.
