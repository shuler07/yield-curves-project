# Единый ETL и запись в PostgreSQL (S2-05)

Команда `python -m src.etl.run` выполняет весь процесс:
MOEX → исходные CSV и manifest → объединение и проверка → восстановление
пропусков → базовая кривая и шесть сценариев → PostgreSQL.
Ставки в CSV остаются процентами, пропуски — `NA`. В БД ставки хранятся в долях;
коэффициенты дисконтирования рассчитываются с годовой капитализацией.

## Подготовка и ручной запуск

Из корня проекта в виртуальном окружении:

```powershell
python -m pip install -r requirements.txt
# При первой настройке скопировать .env.example в .env и задать параметры БД.
docker compose up -d --wait db
python -m alembic upgrade head

# Одна дата.
python -m src.etl.run --date 2026-10-30

# Диапазон включительно.
python -m src.etl.run --date-from 2026-10-27 --date-to 2026-10-30

# При необходимости: явно заданный НОВЫЙ каталог и бюджет скачивания.
python -m src.etl.run --date 2026-10-30 --run-dir downloads/manual-20261030 --timeout 180

# Загрузка в БД из ранее скачанных исходных CSV/ZIP без браузера и сети.
python -m src.etl.run --from-run-dir src/etl/downloads/ИМЯ_ЗАПУСКА
```

Настройки подключения берутся из `DATABASE_URL` либо параметров PostgreSQL
в `.env`, как и у Alembic. Для скачивания нужен Chrome. При повторе используется
диапазон из `manifest.json`, объединение строится заново во временном каталоге
только из перечисленных в нём исходных файлов. Содержимое старого каталога
не изменяется. Правка одного `merged_zcyc_ranges.csv` не изменит результат
повторной обработки. `--from-run-dir` нельзя смешивать с датами и `--run-dir`.

Новая миграция для S2-05 не требуется: достаточно текущей `0003`.
Команды `parse`, `merge` и `postprocessing` сохраняют прежнее назначение;
именно `run` записывает данные в БД.

## Что появляется в БД

Каждый запуск создаёт новую запись `etl_runs`, даже при повторной загрузке:

- `run_type`: по умолчанию `manual`; `scheduled` указывает будущий планировщик
  через `--run-type scheduled` или Python API. Само расписание относится к S2-06.
- `date_from`, `date_to`: запрошенные даты кривых, независимо от даты запуска.
- `started_at`, `finished_at`, `status`: начало, завершение и итог.
- `rows_processed`: число снимков × 12, включая отсутствующие исходные ставки.
- `rows_saved`: число успешно записанных базовых и стрессовых строк, включая
  обновления при повторе; число новых уникальных строк может быть меньше.
  Определения `stress_shocks` в этот счётчик не входят.
- `reason`: каталог файлов и список дат без наблюдений; для `no_data` также причина.
- `error`: ошибка источника либо список дат с ошибками расчёта/публикации.

На каждый снимок (дата + время MOEX) публикуются 12 строк `curve_points` и
6 × 12 строк `stress_curves`. Шесть неизменяемых определений `stress_shocks`
используются повторно для одинаковой версии параметров. Точки связаны с запуском
через `etl_run_id`. Повторное обновление переносит эту ссылку на последний
записавший запуск; `created_at` и идентификаторы существующих точек сохраняются.
Журнал запусков не является архивом прежних значений каждой точки.

Пропуски заполняются только при подготовке публикации: внутри известных сроков —
линейная интерполяция, за их границами — линейная экстраполяция по двум ближайшим
исходным значениям. Ставятся `is_interpolated` / `is_extrapolated`.
Если известных ставок меньше двух, дата завершается ошибкой без публикации.
Вновь загруженные точки получают `is_deleted=false`, в том числе при повторе.

## Транзакции, повтор и исправления

Начало запуска коммитится до обращения к MOEX. Все снимки одной даты, их базовые
точки, определения сценариев и стрессовые точки записываются одной транзакцией.
Ошибка откатывает всю дату, включая изменения существующих точек. Другие даты
продолжают обрабатываться; прежние данные ошибочной даты остаются доступными.
Итог и ошибка записываются отдельной транзакцией после отката.
Если сама БД недоступна, CLI сообщает, что журнал записать не удалось.

Одинаковая дата блокируется через транзакционный advisory lock PostgreSQL:
два процесса могут одновременно скачивать файлы, но публикация одной даты
выполняется последовательно. Разные даты не блокируют друг друга этим механизмом.

Повтор использует upsert по `(curve_date, quote_time, tenor)` для базовых точек
и `(curve_point_id, stress_shock_id)` для стрессовых. Он не создаёт дубли.

Если исходная ставка, коэффициент или флаги восстановления изменились,
загрузчик удаляет устаревшие стрессовые результаты **всех версий** для этого
снимка и записывает шесть актуальных сценариев. Это выполняется в той же
транзакции, чтобы старые сценарии не ссылались на исправленную базу.
Сравнение учитывает точность колонок `NUMERIC`, обычное округление при записи
не считается изменением источника. Другие снимки не затрагиваются.

Если изменилась только конфигурация сценариев, её хеш даёт новую версию:
базовая кривая остаётся той же, новые результаты добавляются рядом со старыми
версиями. Определения `stress_shocks` никогда не обновляются.
После последующего исправления базы старые результаты удаляются по правилу выше;
сами определения и журнал прежних запусков сохраняются.

## Итог и ошибки

CLI выводит UUID запуска, каталог, статус, число сохранённых дат/снимков/строк,
число восстановленных ставок и конкретные даты с ошибками.

| Статус | Значение |
| --- | --- |
| `success` | Все полученные снимки опубликованы |
| `partial_success` | Часть дат опубликована, часть завершилась ошибкой |
| `failed` | Ошибка сбора/формата либо ни одну полученную дату опубликовать не удалось |
| `no_data` | За запрошенный диапазон нет наблюдений |

Полностью отсутствующие даты не интерполируются по соседним дням и не создаются
в БД. При наличии других наблюдений запуск будет `success`, а отсутствующие даты
будут перечислены в выводе и `reason`. Пока нет календаря S2-06, это не объявляется
ни праздником, ни аварией источника. Ошибка источника отличается от `no_data`.
Ошибка общего сбора или проверки CSV возникает до публикации дат этого запуска.

Код выхода: `0` — `success`, `1` — `partial_success` / `failed` / `no_data`
или недоступная БД, `2` — неверные параметры CLI. После частичного успеха можно
повторить весь диапазон без дублей либо отдельно запросить ошибочные даты.

Проверка результата через SQL-клиент:

```sql
SELECT id, run_type, date_from, date_to, status, rows_processed, rows_saved, error
FROM etl_runs ORDER BY started_at DESC LIMIT 10;

SELECT curve_date, quote_time, count(*) AS base_points
FROM curve_points GROUP BY curve_date, quote_time ORDER BY curve_date, quote_time;

SELECT p.curve_date, p.quote_time, s.scenario, s.version, count(*) AS stress_points
FROM stress_curves c
JOIN curve_points p ON p.id = c.curve_point_id
JOIN stress_shocks s ON s.id = c.stress_shock_id
GROUP BY p.curve_date, p.quote_time, s.scenario, s.version
ORDER BY p.curve_date, p.quote_time, s.scenario, s.version;
```

## Программный вызов и проверки

```python
from datetime import date
from src.etl.common import DateRange
from src.etl.pipeline import run_pipeline

result = run_pipeline(DateRange(date(2026, 10, 27), date(2026, 10, 30)))
print(result.run_id, result.status, result.errors)
```

Это синхронная функция для будущего обработчика FastAPI (`def`) и планировщика.
Она управляет отдельными сессиями, возвращает `RunResult` и не запускает HTTP-сервер.
Через `parameters=ScenarioParameters(...)` можно передать другую калибровку;
по умолчанию применяется RUB 400/500/300 б.п. из расчётного слоя.

Интеграционные тесты используют отдельную схему по `TEST_DATABASE_URL`.
Они проверяют реальные коммиты, идемпотентность, параллельные запуски, исправления,
версии сценариев, восстановление пропусков, откат даты и независимый журнал ошибок.
MOEX в тестах заменяется локальными файлами/заглушкой.

```powershell
# Задать URL тестовой PostgreSQL, затем:
pytest tests/db/test_pipeline.py -q
```
