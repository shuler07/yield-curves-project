# Yield Curves

Загрузка кривых бескупонной доходности MOEX, расчёт шести стрессовых сценариев
и сохранение в PostgreSQL. Все команды выполняются из корня проекта.

## Установка

Нужны Python 3.11+, Google Chrome и запущенный Docker Desktop с Linux containers.
Пример для PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

В `.env` задайте `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_PORT`
и согласованный с ними `DATABASE_URL`. По умолчанию БД доступна на `localhost:5433`.
Если порт занят, поменяйте его и в `POSTGRES_PORT`, и в URL.
Переменная окружения `DATABASE_URL` имеет приоритет над `.env`.

```powershell
docker compose up -d --wait db
python -m alembic upgrade head
python -m src.db                 # Проверка подключения
```

Миграции обновляют схему существующей БД. Новые изменения моделей требуют новой
ревизии Alembic. Проверить текущую ревизию: `python -m alembic current`.
`docker compose stop db` останавливает БД с сохранением данных в Docker-томе.
Изменение пароля в `.env` само по себе не меняет пароль уже созданной БД.

## API и автоматическое обновление

```powershell
python -m uvicorn src.api.main:app --host 127.0.0.1 --port 8000
```

[Справочник API](docs/api/index.html) содержит параметры запросов, примеры JSON и
коды ошибок. Swagger UI доступен по адресу **http://127.0.0.1:8000/docs**.

Две ручки читают данные из БД:

| Запрос | Результат |
| --- | --- |
| `GET /curves/raw?date=2026-10-30` | Исходные наблюдения MOEX, без заполнения пропусков |
| `GET /curves/processed?date=2026-10-30` | Базовая и шесть стрессовых кривых, по 19 точек |

Вместо `date` обе ручки принимают `date_from=2026-10-26&date_to=2026-10-30`
(обе границы включены). Ответ содержит `date_from`, `date_to`, `missing_dates`
и `snapshots` с датой и временем котировки. У исходных снимков — `points`, у
обработанных — `curves` с `scenario`, `scenario_version` и `points`.
Ставки, теноры и DF в JSON передаются десятичными строками для сохранения точности;
ставки — в долях, сроки — в годах.

Если запрошенных дат нет в БД, обе ручки сразу запускают ETL для отсутствующих
дат и возвращают результат после загрузки. Соседние пропуски объединяются в
диапазоны; даты с уже готовыми данными повторно не скачиваются. Даже запрос
исходной кривой сохраняет и исходные наблюдения, и все семь обработанных кривых.
У `/processed` неполный набор кривых тоже считается пропуском и восстанавливается.
Первый запрос может ждать скачивания и расчёта; бюджет сбора каждого диапазона
задаётся `ETL_TIMEOUT_SECONDS`. Параллельные запросы используют общую блокировку
с планировщиком и повторно проверяют БД после ожидания.

Такие запуски записываются как `manual`: их инициирует пользователь запросом API.
`scheduled` используется только для фонового расписания.

Для обработанных данных выбирается одна полная версия шести сценариев,
записанная последней по времени начала ETL. Можно указать `scenario_version=…`
для конкретной версии. При подгрузке используется сохранённая калибровка этой
версии; неизвестная версия даёт `404`, неподдерживаемая расчётным слоем — `422`.
Неполные наборы и мягко удалённые точки не выдаются.
Если MOEX не вернула котировки, ответ — `200`, доступные снимки и оставшиеся
`missing_dates` (при полностью пустом диапазоне — пустой `snapshots`).
Ошибка загрузки/расчёта нужных данных даёт `502` с ID запусков из `etl_runs`;
для `/raw` уже сохранённые исходные наблюдения выдаются даже при ошибке расчёта.
Неверные даты дают `422`, недоступная БД — `503`, истёкшее ожидание другого
сборщика — `504`. Результаты успешно загруженных дат остаются в БД при частичном сбое.

При старте API фоновый поток сразу запускает ETL **за текущую дату в Europe/Moscow**,
потом повторяет его каждые 6 часов. В `.env` можно изменить:

```dotenv
ETL_SCHEDULER_ENABLED=true
ETL_INTERVAL_HOURS=6
ETL_TIMEOUT_SECONDS=180
```

Пока API работает, обновление выполняется автоматически; после остановки процесса
обновлений нет. Для сбора нужен Chrome, как и для ручного ETL. Параметр
`ETL_SCHEDULER_ENABLED=false` отключает расписание. Загрузка по запросу остаётся
доступной.
Общая блокировка PostgreSQL исключает параллельные сборы несколькими процессами API;
проверка `etl_runs` предотвращает повтор уже выполненной попытки внутри интервала,
включая перезапуск сервера. У автоматических записей `run_type=scheduled`.
Нет данных за текущую дату — `no_data`, ошибка источника — `failed`; следующая попытка
будет через заданный интервал. Календарь праздников пока не используется.

## Основной запуск: MOEX → расчёт → БД

```powershell
python -m src.etl.run --date 2026-10-30
python -m src.etl.run --date-from 2026-10-26 --date-to 2026-10-30

# Повтор из уже скачанных исходных файлов, без обращения к MOEX:
python -m src.etl.run --from-run-dir src/etl/downloads/ИМЯ_ЗАПУСКА
```

| Параметр `run` | Значение |
| --- | --- |
| `--date YYYY-MM-DD` | Одна дата |
| `--date-from … --date-to …` | Диапазон включительно, вместо `--date` |
| `--run-dir ПУТЬ` | Новый каталог для скачивания; не должен существовать |
| `--from-run-dir ПУТЬ` | Повтор по файлам и диапазону из `manifest.json`; без других дат и `--run-dir` |
| `--timeout 180` | Общий бюджет скачивания в секундах; по умолчанию 180 |
| `--run-type manual` | `manual` по умолчанию; `scheduled` — метка для вызова планировщиком |

Запуск сохраняет исходные `curve_….csv`, `manifest.json` и объединённый
`merged_zcyc_ranges.csv` в уникальном каталоге `src/etl/downloads/`.
В CSV ставки остаются в процентах, пропуски — `NA`. Повтор из каталога читает
исходные файлы манифеста: ручная правка одного `merged_zcyc_ranges.csv` не влияет на него.

Один снимок — дата и время котировки MOEX. Исходные наблюдения сначала сохраняются
в `raw_curve_points`: обычно 12 строк, при пропусках — меньше. Из этой таблицы
читаются ставки, восстанавливаются 19 целевых теноров и рассчитываются шесть стрессов.
Все семь кривых записываются в `processed_curve_points`: 19 базовых + 114 стрессовых
точек = 133 строки на снимок и один набор параметров. В БД ставки записаны
в долях (`0.15 = 15%`), теноры — в годах, дисконтирование: `DF = (1 + r)^(-t)`.
Шесть сценариев: `Parallel_Up`, `Parallel_Down`, `Short_Up`, `Short_Down`,
`Steepener`, `Flattener`. Параметры RUB в [calculations.py](src/etl/calculations.py):
параллельный шок 400 б.п., короткий 500, длинный 300; нижняя граница стрессовых ставок — 0.

Теноры заданы в [common.py](src/etl/common.py): `SOURCE_TERMS` — 12 исходных
сроков MOEX, `TARGET_TERMS` — 19 сроков для расчёта, БД и Excel:
**1 день, 1 месяц, 0.25, 0.5, 0.75, 1, 1.5, 2, 3, 4, 5, 6, 7, 8, 9, 10, 15, 20, 30 лет**.
День — `1/365` года, месяц — `1/12`, округлённые до точности поля `tenor`
(6 знаков): `0.002740` и `0.083333`. Четыре новых внутренних срока интерполируются,
день, месяц и 30 лет экстраполируются. CSV сохраняет только исходные 12 сроков.
Старые файлы можно загрузить через `--from-run-dir`: недостающие семь точек
добавятся к существующим без миграции и дублей. Уже сохранённые даты автоматически
не пересчитываются — для них нужен повторный запуск.

## Отдельные этапы и Excel

```powershell
# Только скачать и объединить CSV, без записи в БД:
python -m src.etl.parse --date 2026-10-30
# parse также принимает --date-from/--date-to, --run-dir и --timeout.

# Повторно объединить исходные файлы каталога, без расчётов и БД:
python -m src.etl.merge --run-dir src/etl/downloads/ИМЯ_ЗАПУСКА

# Рассчитать в памяти и сохранить Excel, без записи в БД:
python -m src.etl.postprocessing --run-dir src/etl/downloads/ИМЯ_ЗАПУСКА --xlsx output/history.xlsx
```

У `postprocessing` вместо `--run-dir` можно задать `--input ПУТЬ_К_MERGED_CSV`.
Без `--xlsx` расчёт остаётся только в памяти. Необязательный `--shock-bps 500`
задаёт всем трём амплитудам одно значение для эксперимента; без него используется RUB 400/500/300.

## Граничные случаи

| Ситуация | Поведение |
| --- | --- |
| Повторный `parse` одной даты | Новый каталог файлов; БД не меняется |
| Повторный `run` того же снимка без изменения источника | Дублей нет. `etl_run_id` обновляется, `id` и `created_at` исходных и обработанных точек сохраняются. В `etl_runs` — новая запись |
| Исправились или исчезли исходные ставки | Исходные строки обновляются, исчезнувшие удаляются. Все семь обработанных кривых всех версий этого снимка удаляются и рассчитываются заново, с новыми `id` и `created_at` |
| Изменились только параметры сценариев | Новая версия сценариев добавляется рядом с предыдущей; справочник параметров не перезаписывается |
| Пропущены отдельные ставки | В CSV остаётся `NA`, в исходной таблице нет строки. Только обработанные кривые получают интерполяцию/экстраполяцию и соответствующие флаги |
| Известно меньше двух ставок снимка | Ошибка расчёта; исходные наблюдения сохраняются, новый обработанный набор даты не публикуется |
| Нет наблюдений за дату | Дата не подменяется соседней. Если весь диапазон пуст — `no_data`; если другие даты есть — `success` со списком отсутствующих дат |
| Ошибка расчёта/записи одной даты | Расчётная часть даты откатывается целиком; исходные данные остаются, остальные даты продолжают загружаться. Итог — `partial_success` или `failed`, ошибка сохраняется в журнале |
| Ошибка скачивания или общего формата файлов | `failed` до публикации кривых этого запуска |
| Два запуска одной даты одновременно | Публикация выполняется последовательно, без дублей |

Архив доступен с `2014-01-01`. Для одной даты сборщик запрашивает также соседний
день и локально оставляет только нужную дату; диапазон через границу года делится
на выгрузки по годам. Нулевая ставка считается значением, а не пропуском.
Календарь праздников пока не используется. Сам ключ CLI `--run-type scheduled`
только помечает запуск; периодические обновления запускает работающий API.

Коды выхода `run`: `0` — успех; `1` — ошибка, частичный успех или `no_data`;
`2` — неверное сочетание/формат параметров. UUID и итог выводятся в консоль.

## Таблицы и проверка данных

| Таблица | Что хранит |
| --- | --- |
| `etl_runs` | Режим, диапазон, время, статус, счётчики и ошибки запуска |
| `raw_curve_points` | Только исходные наблюдения MOEX: дата, время, тенор, ставка без восстановления пропусков |
| `stress_shocks` | Неизменяемые параметры и версии шести сценариев |
| `processed_curve_points` | Базовая и шесть стрессовых кривых: дата, время, тенор, `scenario`, `scenario_version`, ставка, DF и флаги |

`is_deleted` — признак мягкого удаления; повторная загрузка устанавливает `false`.
`rows_processed` — число фактически полученных исходных ставок; `rows_saved` —
записанные исходные и обработанные строки, включая обновления. Полный снимок даёт
12 обработанных исходных ставок и 145 записанных строк. При сбое расчёта в счётчик
входят только сохранённые исходные строки. Журнал фиксируется отдельно.

`scenario = 'Baseline'` обозначает базовую кривую, её `scenario_version = NULL`.
Стрессовые строки ссылаются на `stress_shocks` по паре `(scenario, scenario_version)`.
Схема для dbdiagram.io: [curve-tables.dbml](docs/database/curve-tables.dbml).

Ревизия `0004_raw_processed_curves` переносит старые базовые и стрессовые точки
в общую таблицу. В исходную попадают только старые точки MOEX без флагов
интерполяции/экстраполяции, с ранее сохранённой точностью. Для восстановления
точности исходного CSV можно повторно загрузить каталог через `--from-run-dir`.
Если источник исправился, устаревшие обработанные кривые удаляются даже при ошибке
нового расчёта: они не должны расходиться с исходной таблицей.
Откат миграции восстанавливает прежние таблицы, но не отдельную историю метаданных
исходных строк; при исходных наблюдениях без соответствующей базы он отклоняется.

Подключение через DBeaver/DataGrip: `localhost`, порт и учётные данные из `.env`.
Открыть psql внутри контейнера:

```powershell
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

```sql
SELECT COUNT(*) FROM raw_curve_points;
SELECT scenario, scenario_version, COUNT(*)
FROM processed_curve_points GROUP BY scenario, scenario_version;
SELECT id, status, rows_processed, rows_saved, error
FROM etl_runs ORDER BY started_at DESC LIMIT 10;

SELECT curve_date, quote_time, tenor, scenario, scenario_version, yield_rate, discount_factor
FROM processed_curve_points
WHERE curve_date = DATE '2026-10-30'
ORDER BY scenario, scenario_version, quote_time, tenor;
```

Чтобы **удалить все кривые и историю запусков**, оставив параметры сценариев:

```sql
TRUNCATE TABLE processed_curve_points, raw_curve_points, etl_runs RESTART IDENTITY;
```

